Abstract

   This document specifies the mandatory algorithm transition timetable
   that defines dates for the milestones defined in RFC6916 [RFC6916].
   The timelines for each phase of action in this document may be
   extended if certain criteria are not met, prior to each assigned
   date.  Please consult the current version of this document for latest
   timeline dates.

1.  Introduction

   The Resource Public Key Infrastructure (RPKI) must accommodate
   transitions between public keys used by Certification Authorities
   (CAs).  A less-common transition involves migrating to a new
   signature algorithm suite used by CAs and Relying Parties (RPs).  The
   process to transition to a new, or additional algorithm, is expected
   to completed over a timescale of months or years.  This process of
   transition is defined in [RFC6916].

   This document provides a timetable for the introduction of a new
   algorithm suite broken up into the four phases outlined in Section 4
   of [RFC6916] section 4.  The dates in each section of the timeline
   MAY be extended, but never shortened, if an upcoming date target is
   unable to be met.  Any date changes MUST be logged in Appendix A as a
   list of changes with associated change date.

2.  Terminology

   This document assumes that the reader is familiar with the terms and
   concepts describe in "Algorithm Agility Procedure for the Resource
   Public Key Infrastructure (RPKI)" [RFC6916].  For reference the
   following terms and conventions are provided:

   Algorithm Suite A:  The "current" algorithm suite used for hashing
           and signing.

   Algorithm Suite B:  The "next" algorithm suite used for hashing and
           signing.

   CA Ready Algorithm B Date:  After this date, all non-leaf CAs MUST be
           ready to process a request from a child CA to issue a
           certificate under the Algorithm Suite B.  All CAs publishing
           an [RFC6485] Trust Anchor Locator (TAL) for Algorithm Suite A
           MUST also publish the correspondent TAL for Algorithm Suite
           B.

   CA Go Algorithm B Date:  After this date, all CAs MUST have reissued
           all their signed product sets under lLgorithm Suite B.

   RP Ready Algorithm B Date:  After this date, all RPs MUST be prepared
           to process signed material issued under Algorithm Suite B.

   Twilight Date:  After this date, a CA MAY cease issuing signed
           products under Algorithm Suite A.  Also, after this date, an
           RP MAY cease to validate signed materials issued under
           Algorithm Suite A.

   End-Of-Life (EOL) Date:  After this date, Algorithm Suite A MUST be
           deprecated using the process in Section 10 of [RFC6916] and
           all Algorithm Suite A TALs MUST be removed from their
           publication points.

3.  Algorithm Suite

   The algorithm suite transition this document defines the timetable
   for are listed here as Algorithm Suite A and Algorithm Suite B
   defined in [RFC6485].

3.1.  Algorithm Suite A (from RFC6485)

   *  The signature algorithm used in certificates, CRLs, and signed
      objects is RSA Public-Key Cryptography Standards (PKCS) #1 Version
      1.5 (sometimes referred to as "RSASSA-PKCS1-v1_5") from Section 5
      of [RFC4055].

   *  The hashing algorithm used in certificates, CRLs, and signed
      objects is SHA-256 [SHS].  The hashing algorithm is not identified
      by itself when used in certificates and CRLs, as they are combined
      with the digital signature algorithm (see below).

   *  When used in the Cryptographic Message Syntax (CMS) SignedData,
      the hash algorithm (in this case, the hash algorithm is sometimes
      called a message digest algorithm) is identified by itself.  For
      CMS SignedData, the object identifier and parameters for SHA-256
      (as defined in [RFC5754]) MUST be used when populating the
      digestAlgorithms and digestAlgorithm fields.  NOTE: The exception
      to the above hashing algorithm is the use of SHA-1 [SHS] when
      Certification Authorities (CAs) generate authority and subject key
      identifiers [RFC6487].

4.  Timetable

   The following timetable is considered to be agreed-to by the
   community when this document is accepted as an RFC BCP.  The dates
   for each phase will be agreed upon by the technical contacts at each
   of the five Regional Internet Registries (RIRs), along with a
   majority of CAs issuing RPKI products.

   Dates in this timetable MAY be adjusted when the community shows that
   an adverse effect is likely to take place without an extension.  A
   date change requires a re-publication of this document with an update
   to the transation log in the appendix section.  The re-publication
   MUST be advertised broadly to all RPs and CAs.

6.  Security Considerations

   Algorithm transitions in RPKI should be infrequent events with broad
   community consensus.  This document does not address algorithm
   security or weakness.  However, an algorithm suite change addressed
   in the timetable defined in this document may expose CAs and RPs to a
   vulnerable state from maintaining and running software requiring
   dual-algorithm support for an extended period of time.

   Any CA unable to complete its migration to the new algorithm suite by
   the End-Of-Life date will no longer have a signed product set to be
   validated by RPs.  A CA without a validated, signed product set, will
   expose objects that were formerly VALID in RPKI to UNKNOWN.  These
   RPKI objects may be targets of BGP hijacking until the CA is able to
   produce a signed product set using algorithm suite B.  The community
   is strongly encouraged to monitor the transition process and use all
   possible mechanisms to ensure complete compliance with the new
   algorithm before the EOL date.
